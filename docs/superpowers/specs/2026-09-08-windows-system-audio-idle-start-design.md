# Windows 系统音频静默启动修复设计

## 目标

Windows 输出设备已经被 WASAPI 成功打开时，即使暂时没有电脑声音，Meetily 也应正常开始录音。界面显示“等待电脑声音”，而不是把静默误报为“系统音频不可用”。只有设备确实无法打开时，才引导用户进入 Meetily 的音频设备设置。

## 已确认的根因

当前 Windows 回环代码在 `IAudioClient::Start()` 成功后，继续等待第一批音频数据。两秒内没有数据就返回启动失败。Realtek 输出设备空闲时可能没有数据回调，所以设备已经启动，录音仍被程序主动终止。

前端又把所有包含 `system audio`、`speaker` 或 `output` 的启动错误统一翻译成带有 BlackHole 和 macOS 屏幕录制权限的旧文案，导致 Windows 用户被错误引导。

## 修复设计

1. WASAPI 的初始化、服务获取、回调事件绑定和 `Start()` 全部成功后，立即确认系统音频流启动成功。
2. 没收到音频数据只表示当前没有电脑声音，不能作为启动失败条件，也不能发送录音错误。
3. 收到第一批系统音频数据后，沿用现有 RMS、峰值、时间戳和静音帧统计。
4. 录音状态栏在系统音频回调数为零时显示“等待电脑声音”；收到数据后显示真实音量。
5. 真正的系统音频启动错误保留红色提示，但文案改成平台通用说明，并提供“选择音频设备”按钮，直接打开 Meetily 已有的设备设置窗口。
6. Windows 用户不再看到 BlackHole 或 macOS 屏幕录制权限说明。

## 不在本次范围内

- 不播放未经用户确认的测试音。
- 不擅自修改 Windows 默认输出设备。
- 不把“麦克风 + 系统音频”静默降级为“仅麦克风”。
- 不新增依赖，不重构无关音频处理代码。

## 可验证标准

- 输出设备空闲超过两秒时，录音启动不失败。
- 空闲状态不产生 `SystemAudioNoSignal` 错误事件。
- 状态栏显示“等待电脑声音”，不显示“音频错误”。
- 真正的输出设备启动失败时，可从错误卡片一键打开设备设置。
- 中英文录音文案键完全一致，Windows 可见文案不包含 BlackHole。
- Rust 回归测试、前端契约测试、前端构建和 Rust 编译全部通过。
